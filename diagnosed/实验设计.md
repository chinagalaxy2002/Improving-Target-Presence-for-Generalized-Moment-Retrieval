# SoccerGMR 第一阶段：五项诊断实验的完整计算方案

按照你的要求，第一阶段保留以下五个研究问题：

1. Multi-GT 是否足够多？
2. Decoder Query 是否不活跃？
3. 多个 Decoder Queries 是否重复预测同一个事件？
4. 正确候选究竟没有生成，还是生成后没有被正确选出？
5. 候选定位或分化失败发生在哪一层 Decoder？

我同意你的修改：本阶段应优先统计原生命中数量，而不是把所有现象重新包装成新的指标。

统一规定：

\\[ \boxed{\operatorname{tIoU}(\hat w,g)\geq 0.4\quad\Longrightarrow\quad\text{命中}} \\]

所有主要结果都应是可直接解释的整数：真实事件数、命中事件数、有效 Query 数、重复 Query 数、遗漏事件数，以及每层新增和丢失的命中事件数。

第一阶段只使用冻结的原生 GMR Baseline，覆盖 Moment-DETR、EaTR、QD-DETR、CG-DETR、Sim-DETR、BM-DETR、BAM-DETR、UVCOM，暂不分析 FlashVTG，也不预设 DQ-CGP 有效。

## 一、统一计算约定

为了避免各个实验采用不同的命中定义，首先建立统一的候选—GT 匹配方法。

对于第 \\(n\\) 条文本查询，记它的 GT 为：

\\[ G_n=\\{g_1,\ldots,g_M\\} \\]

模型的全部原生 Decoder Queries 预测为：

\\[ P_n=\\{(p_1,s_1),\ldots,(p_K,s_K)\\} \\]

其中 \\(p_i=[\hat t_i^s,\hat t_i^e]\\) 是预测窗口，\\(s_i\\) 是该 backbone 原生的候选排序分数。这里的 \\(K\\) 是该模型真实的 decoder query 数量，不是固定截断后的 Top-10。

计算每个候选与每个 GT 的时间 IoU：

\\[ IoU(p_i,g_j)= \frac{ \max(0,\min(\hat t_i^e,t_j^e)-\max(\hat t_i^s,t_j^s)) }{ \max(\hat t_i^e,t_j^e)-\min(\hat t_i^s,t_j^s) }. \\]

构造二值命中矩阵：

\\[ B\_{ij}= \begin{cases} 1,&IoU(p_i,g_j)\geq0.4\\\ 0,&\text{otherwise}. \end{cases} \\]

示例：5 个 Decoder Queries、3 个 GT

|         | GT 1   | GT 2   | GT 3   |
| ------- | ------ | ------ | ------ |
| Query 1 | 0.82 ✓ | 0.05   | 0.00   |
| Query 2 | 0.73 ✓ | 0.03   | 0.00   |
| Query 3 | 0.02   | 0.66 ✓ | 0.04   |
| Query 4 | 0.03   | 0.08   | 0.12   |
| Query 5 | 0.00   | 0.05   | 0.51 ✓ |

这个例子中共有 3 个 GT，4 个候选命中了某个 GT，但实际上只有 3 个不同的 GT 被命中；Query 1 和 Query 2 重复命中 GT 1。

为了不把“重复预测一个 GT”算成“找到了多个事件”，每条查询需要保存三种不同的计数：

- 原生命中候选数：有至少一个 \\(B\_{ij}=1\\) 的候选数量。
- 被命中的不同 GT 数：至少被一个候选命中的 GT 数量。
- 一对一独立命中数：每个候选最多匹配一个 GT、每个 GT 最多被匹配一次时的最大命中数量。

第三项通过二分图最大基数匹配计算：先最大化匹配数量，再在相同数量的匹配中最大化 IoU 之和。不能直接按候选分数贪心匹配，否则一个候选同时接近两个 GT 时，可能低估真实可覆盖的事件数。

这三个数字都保留，但以一对一独立命中数作为多时刻定位的主要“命中事件数”。

## 二、实验 1：Multi-GT 是否足够多？

目的：判断 SoccerGMR 是否能够支撑多时刻候选分化这一研究问题。

这项实验完全不需要模型推理，只读取 `relevant_windows`。

对于每条文本查询：

\\[ M_n=|G_n|. \\]

统计：

\\[ N_m=\sum_n\mathbf1[M_n=m]. \\]

建议输出下表：

| 数据统计          | 计算原理                                      |
| ------------- | ----------------------------------------- |
| 负查询数量         | \\(\\#\\{n:M_n=0\\}\\)                    |
| 单 GT 查询数量     | \\(\\#\\{n:M_n=1\\}\\)                    |
| 双 GT 查询数量     | \\(\\#\\{n:M_n=2\\}\\)                    |
| 三个及以上 GT 查询数量 | \\(\\#\\{n:M_n\geq3\\}\\)                 |
| 多 GT 查询总数     | \\(\\#\\{n:M_n\geq2\\}\\)                 |
| 多 GT 中的真实事件总数 | \\(\sum\_{M_n\geq2}M_n\\)                 |
| 涉及多 GT 查询的视频数 | \\(\left\|\\{vid_n:M_n\geq2\\}\right\|\\) |

还要额外检查 GT 之间是否大量重叠，因为两个几乎相同的标注区间未必代表两个独立事件。

我建议将结果按 Standard Val、Standard Test、Full-Decodable Test 分开统计，不合并。Full-Decodable 与 Standard Test 也不能当成两个完全独立的数据集。

关键判断： 如果 \\(M\geq2\\) 的查询很少，那么 SoccerGMR 对“多时刻候选分化”的统计支撑可能不足。此时可以保留这部分作为诊断子集，但不能把多时刻候选分化直接确立为全文的主要问题。

公式实现说明：令交集长度为 \\(I\_{ij}=\max(0,\min(\hat t_i^e,t_j^e)-\max(\hat t_i^s,t_j^s))\\)，严格的 IoU 分母应为 \\((\hat t_i^e-\hat t_i^s)+(t_j^e-t_j^s)-I\_{ij}\\)。前述端点总跨度形式只在两个区间相交时等价。正式计算统一采用交并比的严格定义。

### 2.2 真正发挥作用的 Query 数量

在不设置候选分数阈值的情况下，对全部原生 queries 执行 IoU≥0.4 的一对一最大匹配。

匹配到 GT 的 decoder query 数量为：

\\[ E_n=|\operatorname{Match}\_{0.4}(P_n,G_n)|. \\]

注意，这不是新的性能指标，只是有多少个 query 实际找到了不同 GT的计数。

对 \\(M=1,2,3+\\) 的样本分别统计 \\(A_n(\theta)\\) 和 \\(E_n\\)。

可能出现：

| 现象                | 解释                       |
| ----------------- | ------------------------ |
| Active 数低，独立命中数低  | 可能存在 Query Inactivity    |
| Active 数高，独立命中数低  | Query 被激活，但未找到对应事件，或发生冗余 |
| Active 数高，独立命中数也高 | 能有效利用多个候选                |
| Active 数低，独立命中数较高 | 候选可能已经定位正确，但置信度偏低        |

### 2.3 固定 Query Index 是否长期占据预测？

对于 decoder slot \\(i\\)，在 \\(N\\) 条样本上计算：

\\[ F_i^{active}=\sum\_{n=1}^{N}\mathbf1[s\_{ni}\geq\theta] \\]

\\[ F_i^{hit}=\sum\_{n=1}^{N} \mathbf1[\text{slot }i\text{ 在一对一匹配中命中 GT}]. \\]

还可以统计该 slot 成为 Top-1 的次数。

最终画出所有 query indices 的三个频数柱状图：

- 被激活次数
- 成为 Top-1 次数
- 独立命中 GT 次数

如果模型有 10 个 queries，却长期只有固定两个 indices 命中事件，那么才有证据讨论 Index Collapse。反之，如果 indices 使用很均匀，就不能套用参考论文的结论。

## 四、实验 3：是否重复预测同一个事件？

目的：判断多个 Decoder Queries 是否没有形成独立事件分工，而是重复响应少数 GT。

这个实验必须使用 GT 来定义事件级重复，不能仅凭两个预测窗口的相互 IoU。

对于同一条文本查询：

\\[ T_n=\\#\\{i:\exists j,\ IoU(p_i,g_j)\geq0.4\\} \\]

即所有命中过至少一个 GT 的候选数量。

再计算最大一对一匹配数：

\\[ H_n=|\operatorname{Match}\_{0.4}(P_n,G_n)|. \\]

那么：

\\[ \boxed{D_n=T_n-H_n} \\]

就是命中了真实事件，但在独立事件匹配中多出来的候选数量。

再计算没有命中任何 GT 的候选：

\\[ U_n=K-T_n. \\]

因此全部原生候选可以被分解成：

\\[ \boxed{K=H_n+D_n+U_n} \\]

建议再输出每个 GT 被多少个候选命中：

需要注意：如果两个 GT 本身明显重叠，同一个候选可能命中两者。因此 \\(C\_{nj}\\) 的总和不能直接当作有效 Query 数；独立命中仍以一对一匹配为准。

## 五、实验 4：正确候选没有生成，还是没有正确选出来？

目的：将候选集合失败与候选排序失败分开。这项实验完全使用原生命中数量，不构造新的 IoU 加权指标。

你的修改尤其适用于这个实验。

对每条正查询，计算：

\\[ H_n^{all}= |\operatorname{Match}\_{0.4}(P_n,G_n)| \\]

即使用全部原生候选能够独立命中的 GT 数量。

接着，按照模型原生候选得分 \\(s_i\\) 降序排序，计算：

\\[ H_n^{@k} = |\operatorname{Match}\_{0.4}(TopK(P_n),G_n)|. \\]

建议报告：

\\[ H_n^{@1},\quad H_n^{@3},\quad H_n^{@5}, \quad H_n^{@10},\quad H_n^{all}. \\]

若模型实际只有 \\(K\\) 个 query，则 Top-\\(k\\) 使用 \\(\min(k,K)\\) 个。

### 5.1 未生成的事件数

\\[ \boxed{ N_n^{missing}=M-H_n^{all} } \\]

表示即使检查所有原生候选，仍有多少 GT 无法被不同候选独立命中。

### 5.2 已生成但未进入 Top-K 的事件数

\\[ \boxed{ N_n^{ranking\@k}=H_n^{all}-H_n^{@k} } \\]

表示候选池中已有足够的命中候选，但模型的原生分数排序没把它们全部选进前 \\(k\\) 名。

### 5.3 Top-K 中实际独立命中的事件数

\\[ \boxed{N_n^{selected\@k}=H_n^{@k}} \\]

于是：

\\[ \boxed{ M=N_n^{missing}+N_n^{ranking\@k}+N_n^{selected\@k} } \\]

这三个都是整数，而且严格可加。

例子：3 个 GT、5 个预测候选

| -- | -- | ------- |
| 1  | Q1 | GT1     |
| 2  | Q2 | GT1（重复） |

对于多 GT 查询，Top-1 最多独立命中一个 GT，因此不能简单地把 \\(M-H_n^{@1}\\) 全部叫作排序错误。应重点比较 Top-\\(M\\)、Top-5 和全部候选，确保比较的选取预算足以覆盖所有 GT。

## 六、实验 5：失败发生在哪一层 Decoder？

目的：判断多时刻候选分化失败是在早期候选形成时就已经存在，还是在后续 Decoder Refinement 中出现。

这是与你的层间 DQ-CGP 设计联系最紧密的诊断，但必须先保证每一层的预测窗口来自合法的原生层级输出。

### 6.1 逐层命中数量

对于 decoder 第 \\(l\\) 层，原生预测窗口为：

\\[ P_n^{(l)}=\\{p\_{n1}^{(l)},\ldots,p\_{nK}^{(l)}\\}. \\]

使用完全相同的 IoU≥0.4 规则，计算：

\\[ H_n^{(l)} = |\operatorname{Match}\_{0.4}(P_n^{(l)},G_n)|. \\]

例如：

| Decoder 层 | GT 数 | 独立命中 GT | 重复命中候选 | 未命中候选 |
| --------- | ---- | ------- | ------ | ----- |
| D1        | 3    | 1       | 3      | 6     |
| D2        | 3    | 2       | 2      | 6     |
| D3        | 3    | 1       | 4      | 5     |

这是模拟结果，未必是任何模型的真实行为。

如果模型在 D2 已经覆盖两个 GT，但在 D3 反而只覆盖一个，说明至少存在一个需要进一步解释的后续 refinement 退化现象。

### 6.2 新增命中与丢失命中

令：

\\[ S_n^{(l)} = \\{j:\exists i,\ IoU(p\_{ni}^{(l)},g_j)\geq0.4\\} \\]

表示第 \\(l\\) 层至少被某个候选命中的 GT 集合。

相邻两层之间：

新增命中 GT 数

\\[ N\_{\mathrm{gain}}^{(l\to l+1)} = |S_n^{(l+1)}\setminus S_n^{(l)}|. \\]

丢失命中 GT 数

\\[ N\_{\mathrm{loss}}^{(l\to l+1)} = |S_n^{(l)}\setminus S_n^{(l+1)}|. \\]

持续命中 GT 数

\\[ N\_{\mathrm{keep}}^{(l\to l+1)} = |S_n^{(l)}\cap S_n^{(l+1)}|. \\]

这里用的是“是否被任意候选命中”的 GT 集合，目的是跟踪同一个 GT 是否在层间出现或消失；一对一独立命中数仍应单独报告，避免同一候选覆盖多个重叠 GT 的歧义。

### 6.3 Query Index 的层间迁移

对于允许稳定追踪原生 query index 的 decoder，可以继续记录：

\\[ A\_{ij}^{(l)}=\mathbf1[IoU(p_i^{(l)},g_j)\geq0.4]. \\]

然后对同一 slot 观察它是否：

- 从未命中变成命中；
- 从命中变成未命中；
- 在不同 GT 之间改变负责对象；
- 持续命中同一个 GT。

但是改变负责对象不一定是坏事，因为 decoder refinement 本来就可能调整候选位置。必须结合最终 GT coverage 判断，不能仅凭 slot 变化次数认定发生 collapse。

### 6.4 如何从现有 backbone 取得逐层窗口

优先级如下：

1. 原生 `aux_outputs`： 若包含中间层的 `pred_spans`，直接使用，最可靠。
2. 原生逐层参考点和 span head： 需要按对应 backbone 的实际 reference refinement 逻辑重建该层的输出。
3. 只有 hidden states： 暂时只记录特征，不直接把最终层预测头套在中间层上并把结果称为原生逐层定位。

不同 backbone 的 decoder 深度、auxiliary outputs 和 query update 机制不完全一致，所以需要建立各自的导出适配器，但后续统计公式全部相同。

## 九、如何根据结果判断下一步研究方向？

| 诊断结果                                      | 能够提出的机制问题                                   |
| ----------------------------------------- | ------------------------------------------- |
| 多 GT 查询较多，但 Active Query 数几乎不随 \\(M\\) 增加 | Decoder Query Inactivity / Index Collapse   |
| Active Query 数较高，但重复候选数量很高                | 候选冗余或缺少独立事件分工                               |
| 全部原生候选仍有很多未命中的 GT                         | Candidate Generation / Localization Deficit |
| 全部候选已经命中很多 GT，但 Top-K 命中很少                | Candidate Ranking Deficit                   |
| 某层命中较多 GT，后续层反而丢失                         | Decoder Refinement 中可能出现候选分化退化              |
| D1 就没有找到对应 GT                             | 在 D1 后面插入语义适配未必是首要解决方案                      |
| D1 有不同候选，但后续层逐渐重复或丢失覆盖                    | 值得进一步研究层间 candidate-specific adaptation     |

最后一个判断尤其重要。

只有当逐层诊断证明原生 Decoder 确实存在值得修复的候选分化或定位问题，我们才进一步研究 DQ-CGP 是否适合修复它。

因此，我建议正式执行顺序是：先审计 Multi-GT 分布，再导出全部原生 Decoder Queries，完成命中、冗余、活跃与排序四组统计；最后为各 backbone 补充逐层输出。整个第一阶段不必使用 DQ-CGP 检查点。

这样得到的不是“DQ-CGP 为什么可能有效”的推测，而是一个明确的实验结论：现有模型在多时刻事件定位中，到底在哪一环节遗漏了多少真实事件，以及这些遗漏是如何在 Decoder 内部形成的。
